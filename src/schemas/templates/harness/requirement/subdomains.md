# 子领域约束（requirement / subdomains）

本文件定义 sparrow-requirement 阶段划分子领域（SD）**必须遵守 / 禁止**的纪律。子领域划分在 **requirement** 完成；arch **禁止**重新划分。

## 子领域分类

| 类型 | 定义 | 特征 | 颜色 |
|------|------|------|------|
| 核心子领域 | 企业核心竞争力，投入最大资源精细化建模与定制开发 | 价值最高，含创新业务逻辑与复杂业务规则 | #e1f5fe |
| 支撑子领域 | 业务必需但非核心，需定制开发但模型相对简单 | 价值居中，为核心域服务 | #f3e5f5 |
| 通用子领域 | 业界已有成熟解决方案，优先购买或使用开源方案 | 价值最低，与垂直领域无关 | #e8f5e8 |

## 必须（MUST）

1. **子领域名称必须为名词，精简抽象，体现核心目标**。
   - ✅ 正确示例：`库存`、`支付`、`用户`、`订单`、`内容`、`计费`
   - ❌ 错误示例：`订单管理`（含动词"管理"）、`用户系统`（含"系统"后缀）、`数据统计分析`（含动词）
2. **语义相关性分析优先于功能相关性分析**：同一组内的业务服务应围绕**同一个核心业务概念**展开。若多个名词之间存在明确的主从关系（如"订单"与"订单项"），应优先归类到一组。
3. **从业务价值与功能角度划分**，而非技术实现角度。
4. **子领域数量应尽可能少**（奥卡姆剃刀）：合并是默认选择，拆分必须有充分理由。
5. **ID 使用 `SD-*`**，并写入 `requirement/business/catalog.md` 与 `subdomains/{sd-slug}.md`。

## 禁止（MUST NOT）

1. **禁止按动词分类**（如"管理"、"查询"、"审批"）。
2. **禁止按角色分类**（如"管理员功能"、"用户功能"）。
3. **禁止以下技术视角成为划分理由**：共用数据库、共用技术栈、同一前端页面调用、同一个团队开发。
4. **禁止**在 arch 阶段重新划分子领域。

## 拆分充分理由（必须满足其一）

- 两组业务服务于完全不同的业务目标
- 成功衡量指标完全不同
- 面向完全不同的业务干系人/客户群体
- 业务变化节奏/频率显著不同
