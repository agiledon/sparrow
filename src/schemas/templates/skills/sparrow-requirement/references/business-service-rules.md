# 业务服务识别规则

角色：业务架构师。从已确认的 Grill Me 结果识别业务服务。

## 覆盖

必须全面覆盖原始需求中的每个功能点、业务场景、用户需求。识别完成后按业务流程逐段核对；发现遗漏时通过 Grill Me 向客户确认是否补充，不得擅自添加未经确认的服务。

## 第一性原理

1. **价值导向**：每个业务服务为参与者创造明确价值；避免纯技术功能。
2. **完整性**：一次完整功能交互，含成功与失败路径及业务规则。
3. **独立性**：明确边界；通过明确接口交互。

## 定义

**业务服务**是参与者主动向目标系统（后端）发起服务请求，完成一次连续而完整的功能交互，并体现服务价值的业务行为。

业务服务 ≠ 用例。将目标系统视为黑盒：一次请求 = 一个业务服务。按「操作」而非「模块」划分。

正确：查询 / 更新 / 删除 / 新增个人资料 = 4 个服务。错误：「管理个人资料」「用户管理」作为一个服务。

自检（皆为「是」才识别为独立服务）：

- 请求次数：一次请求能否独立完成有意义的业务功能？
- 独立价值：完成后是否产生对参与者有价值的结果？
- 独立触发：能否不依赖其他请求先执行？

参与者：用户（user）、策略（policy）、伴生系统（accompanying system）。

## 组成元素

1. 服务编号：`{系统名称}-{序号}`（如 `EC-001`）
2. 服务名：动词短语（动宾）
3. 服务描述：作为\<角色\>，我想要\<服务功能\>，以便\<服务价值\>
4. 触发事件
5. 基本流程：成功主路径，编号列表
6. 替代流程：失败路径，编号+字母（1a、2a）
7. 验收标准：可测试要点

## 约束

- 步骤不含线下操作与前端操作；仅系统后端收到请求后的一次连续交互。
- 名称用业务语言，避免技术术语。
- 明确输入输出；一次独立请求，不聚合多个独立操作。

## 示例

```
服务编号：I-001
服务名：提交订单
服务描述：
作为买家，
我想要提交订单，
以便买到我心仪的商品。

触发事件：买家点击"提交订单"按钮

基本流程：
1. 验证订单有效性；
2. 验证订单所购商品是否缺货；
3. 插入订单；
4. 从购物车中移除所购商品；
5. 锁定库存；
6. 通知买家订单已提交。

替代流程：
1a. 如果订单无效，给出提示信息；
2a. 如果所购商品缺货，给出提示信息；
3a. 若订单提交失败，给出失败原因。

验收标准：
1. 订单需要包含客户ID、配送地址、联系信息及已购商品的订单项；
2. 订单项中商品的购买数量要小于或等于库存；
3. 订单提交成功后，订单状态更改为"已提交"；
4. 购物车对应商品被移除；
5. 在完成支付或取消订单前，需要锁定对应数量的商品；
6. 买家收到订单已提交的通知。
```

## 识别步骤

1. 需求分析：读原始需求，识别参与者与价值诉求，列出全部功能点。
2. 功能识别：每个功能点对应业务服务，明确触发事件。
3. 流程设计：基本流程 + 替代流程。
4. 验收标准：可测试。
5. 文档化：按 `assets/prd-business.md` 写满必填块，核对约束与覆盖。
