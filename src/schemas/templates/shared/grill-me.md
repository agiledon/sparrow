# Grill Me

遵守 harness `common/always/interactive-interaction.md`：每次只问一步，给出推荐答案，确认后再问下一问。能查环境、文档或代码的事实不要问。

确认提示：

```
请确认：是（接受推荐答案） / 否（否定推荐答案） / 修改（提供修改后的答案）
```

某一维度已经清晰时不再追问。该维度全部确认后先总结，再进入下一维度。全部维度覆盖后输出快速总结，再写产出。

## 需求探索（requirement 阶段一）

按**问题空间层次**推进，再沿**端到端业务流程**识别业务服务。禁止先堆互不关联的 BS 再事后拼流程。

| 顺序 | 维度 | 对齐 | 说明 |
|------|------|------|------|
| 1 | 域与子领域 | D / SD | 产品边界；子领域划分与 Core / Supporting / Generic |
| 2 | 能力 | C | 各 SD 下「能做什么」；能力少时可内联 |
| 3 | 场景 | S（5W） | Who / Why / When / What / Where |
| 4 | 端到端业务流程 | EBP | 从业务起点到结果的有序步骤；跨 SD 交接须标出 |
| 5 | 业务服务识别 | BS | **沿 EBP 逐步**识别系统请求；一步一 BS（一次请求原则） |
| 6 | 业务规则 / 边界 / 异常 | — | 挂到相关步骤或 BS |
| 7 | 质量属性 | — | 只覆盖实际涉及的非功能维度 |

优先：结构（SD→C→S）→ EBP → 沿链落 BS → 规则与异常 → 质量属性。

快速总结须含：SD 列表与战略类型、关键 C/S、全部 EBP 及步骤→BS 覆盖、参与者、关键规则与质量属性。

写产出前做 E2E 覆盖自检（见 harness `requirement/requirements.md`）：链完整、无遗漏系统步骤、无孤儿 BS。

## UI 探索（requirement 阶段三，可选）

从场景 Who / Actor 推导画像，禁止凭空捏造。

| 顺序 | 维度 | 说明 |
|------|------|------|
| 1 | 用户画像 | 角色属性、目标、熟练度 |
| 2 | 端到端操作流程 | **输入 = 已确认的 EBP**；逐步转为用户操作与系统反馈；可回溯 `EBP-*` |
| 3 | 页面概念 | 操作流程每个触点 → 页面；禁止与流程无关的页面 |
| 4 | 视觉偏好 | 风格、色调、密度 |
| 5 | 客户端类型 | Web / 移动 / 桌面 |
| 6 | 可访问性 | 国际化、无障碍、响应式 |

顺序：画像（按 Actor）→ **操作流程（← EBP）** → 页面 → 视觉与客户端。

禁止另起与 EBP 脱节的「用户旅程」作为主输入。操作流程无断点；禁止孤儿页面。落地到 ui-spec 与原型，原型须能走通对应操作流程。
