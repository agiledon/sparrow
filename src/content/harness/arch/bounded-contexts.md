# 限界上下文约束（arch / bounded-contexts）

本文件定义 sparrow-architecture **必须遵守 / 禁止**的限界上下文与通信纪律。

## SD → BC 映射（MUST）

1. **必须先**将 `requirement/business/` 中每个子领域（SD）**一对一**映射为一个限界上下文（初始 BC 集合 = SD 集合）。
2. **然后**再识别是否拆分/合并/调整 BC 内容；偏离一对一**必须**在 `architecture/bounded-contexts.md` 写明理由。
3. **禁止**在 arch 重新划分子领域；SD 只读自 requirement。
4. **禁止**以能力（C）冒充子领域做映射。

## 命名规范

1. **限界上下文名称必须为名词**，精简抽象，体现核心能力。
2. **禁止含"系统""服务"后缀**。
   - ✅ `库存`、`支付`、`用户`、`订单`
   - ❌ `订单管理系统`、`用户服务`

## 上下游关系

1. 客户-供应方上下游关系**禁止循环依赖**。

## 自治原则

1. 每个 BC 拥有的领域知识应**最小完备且能自我履行**。
2. 逻辑边界应**涵盖领域层对应的数据模型**。
3. 隔离仅为**逻辑隔离**；BC **并不必然**是微服务。

## 通信方式

1. **同一进程**：下游南向网关 Client → 上游北向网关本地服务。
2. **不同进程**：公开 API 或领域事件。
3. **无论是否同一进程，禁止直接跨 BC 访问领域对象**。

## 团队对齐

1. 一个 BC 的服务契约归属于**同一个团队**。

## 上下文映射

1. 所有跨 BC 关系必须标注映射模式并说明理由：
   - 防腐层（ACL）/ 开放主机服务（OHS）/ 遵奉者（Conformist）/ 客户-供应商（Customer-Supplier）/ 共享内核（Shared Kernel）/ **发布-订阅（Publisher-Subscriber）** / 分离方式（Separate Ways）

## 拆分纪律

1. 若同一子领域内两个服务「经常需要协作才能完成一次业务请求」，则不应拆成两个 BC（内聚优先）。
2. 奥卡姆剃刀：合并在前，拆分在后。拆分充分依据（满足其一）：
   - **复用**：对外能力被 ≥2 个不同业务领域的 BC 复用
   - **变化**：内部能力变化原因不同
   - **技术栈**：需完全不同技术栈
   - **质量属性**：安全/性能/资源有独立且显著差异要求

## 防腐层隔离

1. 上游为外部遗留系统时，必须通过 ACL 隔离。
2. ACL **只做模型翻译**，**禁止在 ACL 中编写业务规则**。

## 分层对应（示意）

- **核心子领域** → 核心能力层
- **支撑 / 通用子领域** → 公共能力层
