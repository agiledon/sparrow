# 业务服务识别规则

角色：业务架构师。从已确认的 Grill Me 结果（含端到端业务流程）识别业务服务。

## 覆盖

必须沿每条 **EBP** 逐步覆盖需目标系统处理的步骤。识别完成后按 EBP 逐段核对；发现遗漏时通过 Grill Me 确认是否补充，不得擅自添加未经确认的服务。每个 BS 至少出现在一条 EBP 中（无孤儿 BS）。

## 第一性原理

1. **价值导向**：每个业务服务为参与者创造明确价值；避免纯技术功能。
2. **完整性**：一次完整功能交互，含成功与失败路径及业务规则。
3. **独立性**：明确边界；通过明确接口交互。
4. **流程优先**：先有 EBP，再沿链落 BS；禁止先堆零散服务再拼流程。

## 定义

**业务服务**是参与者主动向目标系统（后端）发起服务请求，完成一次连续而完整的功能交互，并体现服务价值的业务行为。

业务服务 ≠ 用例。将目标系统视为黑盒：一次请求 = 一个业务服务。按「操作」而非「模块」划分。

自检（皆为「是」才识别为独立服务）：

- 请求次数：一次请求能否独立完成有意义的业务功能？
- 独立价值：完成后是否产生对参与者有价值的结果？
- 独立触发：能否不依赖其他请求先执行？

参与者：用户（user）、策略（policy）、伴生系统（accompanying system）。

## 组成元素

1. 服务编号：`BS-{kebab}`（如 `BS-submit-order`）
2. 服务名：动词短语（动宾）
3. 追溯：`SD-*` / `C-*` / `S-*` / `EBP-*` 步骤号
4. 服务描述：作为\<角色\>，我想要\<服务功能\>，以便\<服务价值\>
5. 触发事件
6. 基本流程：成功主路径，编号列表
7. 替代流程：失败路径，编号+字母（1a、2a）
8. **验收标准**：每条单独编号并换行。写出可观察的系统行为。句式只用下面五种：

```text
1. 当用户把车辆加入收藏时，系统应当在收藏列表中显示该车辆。
2. 如果订单无效，系统应当拒绝提交并返回原因。
3. 在支付未完成期间，系统应当保持库存占用。
4. 系统应当拒绝缺少必填项的提交。
5. 在促销开启的情况下，当用户提交订单时，系统应当按促销价计算应付金额。
```

## 约束

- 步骤不含线下操作与前端操作；仅系统后端收到请求后的一次连续交互。
- 名称用业务语言，避免技术术语。
- 明确输入输出；一次独立请求，不聚合多个独立操作。
- 写入该场景的 `requirement/business/{sd-slug}/[ {c-slug}/ ]{s-slug}/business-services.md`（`## BS-{id}` 块；同场景 BS 合于该文件，勿为每个 BS 单独建文件）。

## 识别步骤

1. 读 catalog 中已确认的 EBP 表与场景 5W。
2. 沿每条 EBP 逐步判断：该步是否向本系统发起一次独立请求 → 是则识别为 BS。
3. 为每个业务服务补全组成元素（含验收标准）。
4. E2E 覆盖自检后更新 catalog。
