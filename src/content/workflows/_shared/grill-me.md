# Grill Me

遵守 harness `common/always/interactive-interaction.md`：每次只问一步，给出推荐答案，确认后再问下一问。能查环境、文档或代码的事实不要问。

确认提示：

```
请确认：是（接受推荐答案） / 否（否定推荐答案） / 修改（提供修改后的答案）
```

某一维度已经清晰时不再追问。该维度全部确认后先总结，再进入下一维度。全部维度覆盖后输出快速总结，再写产出。

## 需求探索（requirement 阶段一）

顺序以 harness `requirement/requirements.md`「需求结构 V 模型」为准。左侧自顶向下识别，右侧自底向上归纳。禁止先划子领域，也禁止先堆互不关联的业务服务再事后拼流程。

| 顺序 | 维度 | 说明 |
|------|------|------|
| 1 | 利益相关者（Stakeholder） | 先识别利益相关者，再确定参与者：外部客户与内部用户 |
| 2 | 价值流（Value Stream） | 一组端到端活动，为客户或内部用户创造一个有价值的结果；说明创造什么价值、如何创造 |
| 3 | 端到端业务流程 | 从参与系统的利益相关者出发（用户角色、系统或定时策略），在价值流指导下整理旅程 |
| 4 | 业务服务（Business Service） | 把流程中的业务活动识别为业务服务并命名；一次请求原则 |
| 5 | 业务场景（Scenario） | 仅当达到问题空间复杂度阈值（Problem-space Complexity Threshold）：按业务相关性与场景五问归纳 |
| 6 | 业务能力（Capability） | 仅四层时：由场景归纳；不能独立运作则合并，拆开仍能独立运作或有多个责任主体则再拆 |
| 7 | 子领域（Subdomain） | 从业务问题和目标归纳；未达问题空间复杂度阈值时直接由业务服务归纳。判定核心 / 支撑 / 通用 |
| 8 | 业务规则 / 边界 / 异常 | 挂到相关步骤或业务服务 |
| 9 | 质量属性 | 只覆盖实际涉及的非功能维度 |

未达问题空间复杂度阈值时跳过第 5、6 行，不确认场景与能力。阈值只定义在 harness `requirement/requirements.md`，此处不重复数字。

快速总结须含：利益相关者与参与者、价值流、全部端到端业务流程及步骤到业务服务的覆盖、已命名业务服务、子领域及类别、关键规则与质量属性。四层时另含场景与能力。

写产出前做覆盖自检（见 harness `requirement/requirements.md`）：链完整、无遗漏系统步骤、无孤儿业务服务。

## UI 探索（requirement 阶段三，可选）

四层时从场景的「谁」推导画像；两层时从已确认的参与者推导。禁止凭空捏造。

| 顺序 | 维度 | 说明 |
|------|------|------|
| 1 | 用户画像 | 角色属性、目标、熟练度 |
| 2 | 端到端操作流程 | **输入 = 已确认的 EBP**；逐步转为用户操作与系统反馈；可回溯 `EBP-*` |
| 3 | 页面概念 | 操作流程每个触点 → 页面；禁止与流程无关的页面 |
| 4 | 视觉偏好 | 风格、色调、密度 |
| 5 | 客户端类型 | Web / 移动 / 桌面 |
| 6 | 可访问性 | 国际化、无障碍、响应式 |

顺序：画像（四层按场景的「谁」，两层按已确认的参与者）→ **操作流程（← 端到端业务流程）** → 页面 → 视觉与客户端。

禁止另起与 EBP 脱节的「用户旅程」作为主输入。操作流程无断点；禁止孤儿页面。落地到 ui-spec 与原型，原型须能走通对应操作流程。
